### 1.4 The two lanes are not partitioned. They contest the same directives.

Three independent contention surfaces were identified by reading the queue
logic in both files.

**(a) Identical, unclaimed queue query.** Both daemons issue the same
`mesh_memory` SELECT — same `agent_id` filter, same `memory_type` filter, same
ordering — differing only in `LIMIT`:

- `zo_sentinel_builder.py:869-873` (LIMIT 10)
- `goose_runner.py:271-278` (LIMIT 20)

Neither takes a lock, writes a claim, nor updates row status on read. Two
readers of the same ordered head of the same queue.

**(b) The mesh builder reverses the goose lane's completions.**
`auto_restore_failed_directives()` at `zo_sentinel_builder.py:843-866` globs
`directives/*.done.json` — the exact sentinel files the goose lane writes at
`goose_runner.py:1209` — and renames them back to `.json` whenever the declared
output is absent or fails a smoke test, re-admitting the directive into the
builder's own file queue. This behaviour is confirmed present in the builder's
service log on 2026-08-23.

This also defeats the apparent directory partition. The builder globs
`directives/*.json` and the goose lane globs `directives/pending/*.json`, which
look disjoint — but surface (b) injects work into the builder's queue directly
out of the goose lane's sentinel space.

**(c) No shared completion protocol.** The goose lane signals completion by
writing `directives/{directive_id}.done.json`. The mesh builder signals
completion of a mesh-sourced directive by writing a `build_complete` row to
`mesh_memory` (`zo_sentinel_builder.py:915-920`), which the goose lane never
reads. Each lane's dedupe mechanism is invisible to the other.

### 1.5 The contention is visible in the data

**449 of 4,897 distinct directives (9.2%) in the trailing 30 days carry
provenance rows from both lanes.**

The recurring signature: the goose lane attempts a directive repeatedly and
records `success=false, smoke_result=ghost`; the mesh builder subsequently
records `success=true, smoke_result=pass` on the same `directive_id`. Observed
on `build_axis_evidence_api_router` across nine goose attempts spanning
2026-07-31 to 2026-08-24, closed by the mesh builder at 01:45:30Z.

The differing `directive_type` / `complexity` values between the two lanes
(`utility`/`medium` versus `code`/`high`) are each lane's own self-classification
of the same directive. They are not evidence of a routing partition.

### 1.6 Queue state at time of observation

Builder-eligible top-level directives: 0. `pending/`: 0. Open mesh directives: 0.
148 `.ghost.json`, 5,465 `.done.json`. Contention is bursty — it occurs when the
architect emits a batch, not continuously.

### 1.7 The archival record is misleading

`zo_mesh` HEAD is `81d14b0 chore: archive retired zo_sentinel_builder.py (dead,
graph-verified)`. That commit moved a **2026-05-25** copy of the file into
`archive/`. A newer copy dated **2026-08-22**, untracked by git, remains at
`zo_mesh/zo_sentinel_builder.py` and is the file the running process is
executing. The two files differ.

The graph verification that declared the builder dead was performed against the
archived copy, not against the copy in service. The "dead, graph-verified"
claim in the commit message does not describe the running system.

### 1.8 Unresolved

Which lane is canonical is **not settled by this evidence and remains open.**
Build volume favours the goose lane by roughly 12:1. Success on contested
directives favours the mesh builder, which is closing work the goose lane has
repeatedly ghosted. Retiring the mesh builder on volume alone would strand the
449-directive contested tail.

## 2. Inference routing: the README is wrong, and there are two routing surfaces

### 2.1 The mesh router does not use MiniMax or Gemini

The README states `inference_router_service.py:8773` runs a MiniMax → Gemini →
Ollama cascade. The file contains **zero** occurrences of either "minimax" or
"gemini", case-insensitive. That description does not match the code.

### 2.2 The real tier set

Tiers reachable in `inference_router_service.py`: **`ollama`, `tower`, `haiku`,
`sonnet`.**

- The `ROUTING` table maps task types onto `ollama`, `tower`, and `sonnet`.
- `haiku` is the default for any unmapped task type (`inference_router_service.py:258`)
  and the terminal fallback on tier failure.
- Escalation is `tower` → `ollama` → `haiku` (`inference_router_service.py:266-292`),
  and `ollama` → `haiku` (`inference_router_service.py:306-315`).

The competing record describing tiers as `ollama` / `ollama_fallback` / `haiku` /
`sonnet` is closer to the truth than the README, but still wrong on two points:
it omits the `tower` tier entirely, and `ollama_fallback` is not a tier. It is a
logging label — `inference_router_service.py:175` appends a `_fallback` suffix to
the tier name when recording an inference that fell back.

### 2.3 The mesh router and the ladder shim are two separate routing surfaces

They are not the same surface.

| | mesh router | ladder shim |
|---|---|---|
| file | `zo_mesh/inference_router_service.py` | `zo_sentinel/ladder_shim.py` |
| port | 8773 | 8796 |
| interface | `/complete`, bespoke | `/v1/chat/completions`, OpenAI-compatible |
| tiers/rungs | 4 tiers (above) | 16-rung ladder, single advertised model id |

The ladder shim exists specifically because the goose binary is single-provider
per session; the shim presents the whole ladder behind one OpenAI-compatible
endpoint (`ladder_shim.py:5-25`).

Consumers:

- `zo_sentinel_builder.py:72` → mesh router (8773) **only**.
- `goose_runner.py:52` → mesh router (8773); `goose_runner.py:88,1893` → ladder
  shim (8796), which it also sets as the goose subprocess's OpenAI base URL.

So the goose lane touches **both** surfaces; the mesh builder touches **one**.
The `zo-ladder-*` model strings in `build_provenance` originate from the shim.

### 2.4 Known operational note

The upper rungs of the ladder require a provider credential that has been
observed unset in the past, causing those rungs to fail and builds to flatten
onto a lower rung (`ladder_shim.py:254,317,346-355`). Whether that credential is
currently set was not verified in this session.
