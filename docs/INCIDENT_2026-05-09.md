# Incident postmortem — 2026-05-09: directive builder overwrote `ui_server.py` with a 9.8 KB stub

## Summary

The "rich" `ui_server.py` (≈30 KB, 796 lines, 9 routes, inline CSS+JS,
exception middleware, Pydantic `SubmitRequest`) was replaced on disk by a
9,800-byte stub generated by the directive-builder daemon. The stub kept
the service constants and DB helpers but stripped every route except a
couple of healthcheck-shaped placeholders. There was no `.bak` on disk,
no git working tree, and no copy in any reachable cache, so a clean
rollback was impossible.

The reconstructed file (this repo's `ui_server.py`) was rebuilt from:

* the captured client-side JS that the previous server returned (the
  `loadRecent → doSearch → renderResult` flow), audited earlier in the
  day before the overwrite;
* the surviving on-disk template fragments at
  `/home/workspace/zo_sentinel/{dashboard.html, mcp_submission_portal.html, sentinel_status.html}`;
* the post-overwrite stub itself, which retained the DB-call patterns
  (`ws_write` / `ws_query` / `ws_execute`), service constants, heartbeat
  loop, and PID-file single-instance lock — those were copied verbatim
  so behaviour against `write_service` / `query_service` stays identical.

## Root cause

The directive-builder treated a directive of the form
`output_file=ui_server.py` as a **rewrite-from-scratch** operation
rather than a patch. It:

1. Did not snapshot the existing file to a `.bak` before writing.
2. Did not branch / open a PR — it wrote directly into the live tree.
3. Did not diff the new content against the old, so the size collapse
   from ~30 KB to ~10 KB raised no warning.
4. Had no rollback handler when the resulting service started returning
   404s.

The directive prompt was small enough that the LLM produced a minimal
stub that satisfied the literal prompt ("FastAPI app with `/healthz`")
without considering what the existing file contained.

## Why no rollback was possible

* The `zo_sentinel` directory was not under version control. The
  surrounding repos are git-managed but this subtree had been
  deliberately excluded so directive-builder writes wouldn't churn the
  history.
* Supervisord was running the file from disk directly — there was no
  artifact registry, container image, or release tarball with a prior
  version.
* The previous file was not in any rsync snapshot; the on-disk backup
  daemon was scheduled for nightly and had not yet captured the
  pre-overwrite state.

## Lessons

1. **Source of truth in git.** Service code must live in a repository
   (this one). Supervisord pulls from a checkout, not from a bare
   working directory.
2. **Builder must clone-branch-PR, not direct-write.** The directive
   builder is permitted to write to a branch and open a PR. It must
   never write to the deployment path. A human (or a separate gate)
   merges.
3. **Mandatory backup before any rewrite.** Any directive that
   overwrites an existing file must first snapshot the current contents
   to `<file>.bak.<utc-iso>` and to a write-once side store. The
   directive fails closed if the backup write fails.
4. **Distinguish patch vs. rewrite directive handlers.** "Patch the
   `/api/recent` handler" and "rewrite the entire UI server" are not
   the same operation and should not share a code path. The patch
   handler must apply diffs to a parsed AST or to a known anchor;
   rewrites require explicit `--allow-rewrite` plus a backup confirmation.
5. **Size-delta sanity check.** A rewrite that collapses a file from
   ~30 KB to ~10 KB (or removes more than N% of the routes the previous
   file exposed) should require explicit operator confirmation.
6. **No silent restart on file change.** Supervisord watchers must not
   restart a service whose route surface has shrunk by more than a
   small threshold without producing an alert.
7. **Co-located project files.** ZO MESH `dashboard.html` was
   incorrectly co-located in `zo_sentinel/templates/` — should live in its
   own repo.
