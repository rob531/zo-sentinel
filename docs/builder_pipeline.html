01

The shape of it

Two files carry the whole system. zo_mesh/zo_sentinel_builder.py (1,245 lines) is the daemon: directive intake, prompt assembly, validation, and every side effect that outlives the process. zo_sentinel/escalation.py (1,235 lines) is the router: a cost-ordered ladder of models with rate limiting, quota parking, and a daily spend cap.

The builder never names a model. It calls escalation.ask("generate", …) and gets back whichever rung answered. Everything specific to a provider — auth, payload shape, reasoning-tag stripping, tool-call parsing — lives behind the adapter boundary.

The governing assumption is that generation is unreliable and cheap, and verification is reliable and cheaper still. So the builder generates optimistically, then spends most of its code deciding whether to keep the result.

02

Stage by stage

The twelve steps a cycle actually executes, in order. Function names are the live symbols in zo_sentinel_builder.py.

00

Boot run()

Reads KNOWLEDGE_BASE.md into the module-global KNOWLEDGE, logs whether the escalation ladder imported and whether a legacy MiniMax key is present, then runs auto-restore before the first cycle.

Auto-restore walks directives/*.done.json and quietly smoke-tests each declared output. A directive whose artifact is missing or now broken is renamed back to .json and rebuilt — capped at MAX_AUTO_RESTORES = 3 per task so a permanently unbuildable directive cannot loop forever.

01

Heartbeat mesh_heartbeat()

Each cycle opens and closes with a row into service_health on the write service at :8772. Liveness is a side effect of doing work, not a separate timer — a wedged cycle stops the heartbeat.

02

Intake load_file_directives() + load_mesh_directives()

Two sources, concatenated. Files: directives/*.json, skipping anything containing .done., .bak., or .ghost., plus any directive whose status is already done — then sorted by priority descending, defaulting to 0.5.

Mesh: a SQL read against mesh_memory for agent_id='zo_sentinel.directive' and memory_type='build_directive', ordered by importance, capped at 10. A malformed file directive with no task identity is logged and dropped rather than guessed at.

03

Normalize normalize_directive()

Three directive schemas converge on one internal shape of task / description / output_file. Schema 2 maps directive_id → task and goal → description, folding constraints and success_criteria into the description as labelled blocks. Schema 3 maps key → task and spec → description, and where no output path was given it regex-extracts one from the spec prose — first a zo_sentinel/…​.py path, then a logs/…​.py fallback. Defaults land at handler=generate_file, complexity=high.

04

Dispatch process_directive()

Looks up one of three handlers — generate_file, write_raw, run_script — and clears _LAST_GEN_META so provenance cannot leak between directives. The whole call is wrapped so that mark_directive_done() runs in a finally block: a directive that raises is still retired, which is what stops a poison directive from being retried every 300 seconds forever.

05

Pre-flight guards build_task_generate_file()

Rejects an output_file that resolves to a directory, creates parent directories, then checks idempotency. The key is md5(task:output_file:description[:100])[:16], and a registry hit alone is not enough — the file must still exist and still pass a quiet smoke test. A previously-built file that has since broken is rebuilt, not skipped.

06

Prompt assembly build_rich_prompt() / build_compact_prompt()

Two prompts are built every time. The rich prompt carries the base context, the knowledge base, the running build state, and the first 60 lines of each declared dependency. The compact prompt carries a hard-coded rules digest plus truncated slices — build state to 300 chars, deps to 400, description to 350.

Base context forks on file type: Python files get "output only raw Python", .html files get a stricter contract that also fixes the visual style. House conventions from builder_conventions.json are appended to both base contexts at import time, so adding a learned rule to that file changes every future build with no code edit.

07

Generate smart_generate()

Complexity picks the prompt — high and medium get rich, low gets compact — and the call goes out as escalation.ask("generate", …) at max_tokens=8192, temperature=0.3, max_attempts=4.

Returned text is stripped of reasoning preambles a second time at the builder boundary and validity-checked before it is accepted. Any failure here — exception, empty text, or invalid content — returns an empty string, which drops smart_generate into the preserved v1.9.5 MiniMax → Ollama cascade.

08

Validate and write content_is_valid() → atomic_write()

Content must clear 300 bytes and contain none of the nine error signatures — provider error strings like credit balance is too low and Error code: 402 that would otherwise be written to disk as source code. Markdown fences are stripped after validation, not before.

wiring_check() scans for four house anti-patterns and warns without blocking. The write itself goes to a dotfile temp in the same directory and is moved into place, so a reader never sees a partial file.

09

Smoke test smoke_test_file()

For Python outputs, a dependency pre-flight runs first — auto_dependency_resolver.py is loaded by file path and may install missing imports. Then the file is checked by suffix, and Python files that survive the static gates are actually executed in a subprocess with time.sleep stubbed out and a 15-second timeout.

10

Rescue smart_generate_with_rescue()

On a smoke failure the traceback is fed back into a fresh prompt as PREVIOUS FAILURE:, at temperature=0.2. The result is re-validated, re-written, dependency-resolved, and re-smoked. A second failure is terminal: a build_failed mesh event at ERROR severity, a manifest row, and a registry entry of smoke_fail.

11

Record five destinations

A success writes to all of: BUILD_STATE.md (upserted by output file, so a rebuild replaces rather than appends), BUILD_MANIFEST.md, a build_complete mesh event, a build_artifact mesh memory at importance 0.78, and the local .build_registry.json.

Then two forward moves: inject_next_directive() writes any chained follow-up as a new directive file at slightly lower priority, and if every file a phase expects is now present, run_phase_checkpoint() re-smokes the whole phase and records the result.

12

Close evict_ollama()

Every cycle ends by posting keep_alive: 0 for all three local Ollama models, releasing their weights from memory before the daemon sleeps. On a box that also runs the mesh services, holding three model weights across a five-minute idle is the expensive default.

Four gates before any rung is called

Tool capability — a text-only rung is skipped when the caller passed tools. Rate limit — a sliding 60-second window per model id. Quota — a rung near its wall, or parked after a 429, is skipped proactively and recovers when its bucket resets. Cost — a paid rung is blocked outright unless the task type is in PAID_OK_TASKS, and then still has to fit under the 5.0/day priority budget.

PAID_OK_TASKS defaults to builder_critical alone. Every other task type is hard-capped to free rungs — it exhausts and lets the caller fall back rather than cascading into Sonnet or Opus on a routine build.

04

What counts as working

The smoke test is the only thing standing between a plausible-looking generation and a file that ships. It branches on suffix.

SuffixCheckExecuted?
.htmlParsed with html.parser; parse errors failno
.shMust open with a shebangno
.sqlMust open with SELECT / WITH / INSERT / UPDATE / DELETE / CREATE / ALTER / DROPno
.md .txt .json .yaml .conf .jsx .tsxLength and error-signature gates onlyno
.py (uvicorn)Anti-patterns + ast.parse; execution deliberately skipped for daemons that would bind a portno
.pySix wiring anti-patterns, then ast.parse, then real import in a subprocess with time.sleep stubbed and PYTHONPATH setyes

The six anti-patterns are house-specific and encode past outages: calling write_service() as a function instead of POSTing to :8772, sending 'row' where the service expects 'rows', DuckDB calls that do not exist (executescript, INSERT OR IGNORE), and direct duckdb.connect() that bypasses the write service entirely. A file can be perfectly valid Python and still fail here.

Catching SystemExit as a pass is deliberate — a module that parses args and exits is working correctly, not broken.

05

Worth knowing before you touch it

Four things the code does that the comments around it no longer describe accurately.

Directive complexity does not select a ladder tier

zo_sentinel_builder.py:657  ·  escalation.py:242

escalation.py defines a complexity-routed map — builder_low at rung 0 through builder_critical at rung 15 — but the builder always passes the literal task type "generate", which starts at rung 0 regardless. Inside the builder, complexity only chooses rich versus compact prompt and shapes the legacy fallback. The tiered entry points are reachable only through the goose_runner / ladder_shim path via GOOSE_MODEL, and a "critical" directive submitted as a file gets the same rung-0 start as a trivial one.

The ladder docstring predates the ladder

zo_sentinel_builder.py:636–639

It documents "rungs 1–6 Gemini, rungs 7–8 Zo free, rungs 9–12 Zo paid". The live ladder has Gemini and Gemma at 2–10, Zo free at 11–12, and Zo paid at 13–16 — the MiniMax-M3 and Gemma rungs were inserted after the comment was written. The code is correct; the map in the docstring is off by several rungs and will mislead anyone reading it to reason about routing.

An invalid ladder response triggers the entire legacy cascade

zo_sentinel_builder.py:710–715

_smart_generate_via_ladder returns an empty string for three different situations — the call raised, the text came back empty, or the content failed validation. All three look identical to smart_generate, which then runs the full v1.9.5 MiniMax → Ollama path. So a ladder response that was merely 40 bytes short of MIN_VALID_BYTES costs a second full generation attempt on local models, after up to ten ladder calls have already been made.

Two write-service payload shapes are in use

zo_sentinel_builder.py:802  ·  escalation.py:1065

The builder's ws_write sends "rows" as a bare dict, matching the house rule it injects into every prompt. The ladder's telemetry writer sends "rows" as a list of one dict. Both target :8772/write and both are presumably accepted, but the builder also smoke-fails any generated file containing 'row': — so the convention it enforces on its output is stricter than the one its own dependency follows.
